# CLAUDE.md

Guidance for Claude Code (or any future contributor) working in this repo.

## What this is

**The Daily Tape** is the website for the Neeley Equity Research Club, a
student equity research club at TCU organized into sector "pods." Its design
is modeled closely on mktbrief.com: Playfair Display headlines, IBM Plex
Sans/Mono body and data text, an ink-black + warm-gold palette, and a
kicker → headline → italic deck → byline → body article structure — meant to
read like an actual AI-generated market newsletter, not a generic SaaS
dashboard. See `README.md` for setup/run instructions. `SITE_NAME` (the only
place the publication name is defined) is at the top of `templates/partials.js`.

**Both the homepage's Today's Brief and every pod's sector brief are
AI-generated**, written by the daily cron (see below) — nobody at the club
writes or reviews them before they're published. A club member can still
curate a pod by hand-editing its Markdown file (pinning it, flagging a
Watchlist, adding a one-off manual entry), but the default daily content is
fully automated. Don't write copy anywhere on the site that implies a "pod
lead" writes these by hand — that's no longer accurate.

## Tech stack and philosophy

- Plain HTML/CSS/JS. No frontend framework, no bundler, no CSS preprocessor.
- Zero npm dependencies. The build script and API function use only Node's
  built-ins (`fs`, `path`, global `fetch`).
- Static site generated at build time from Markdown; the only runtime/dynamic
  piece is the Market Pulse strip on the homepage, backed by one Vercel
  Serverless Function running on a daily cron.
- Deploy target is Vercel, using its git integration (push to `main` → auto
  rebuild → auto deploy) plus a `crons` entry in `vercel.json`.

Keep it this way. This project is intentionally simple so non-technical club
members can read and modify it later. Don't introduce a framework, a
templating library, a markdown-parsing dependency, or a database — the
content model and build script are deliberately hand-rolled because the input
format (see below) is small and fixed.

## Content model (important — read before touching pod pages)

Each pod's content is a single Markdown file in `content/pods/`. There is no
CMS, no admin panel, and no database for pod content — the daily cron rewrites
each file automatically (see "Sector brief generation" below), and a club
member can still edit a file directly for manual curation. The format is fixed:

```markdown
---
pod: Financials & Real Estate
pinned: true
sample: true
---

## Watchlist
- $JPM: Reports Q3 earnings before the open

## 2026-09-15
**Headline goes here**
A few sentences of analysis.
Tickers: $PNC, $KEY
Sources: Company 10-Q, earnings call transcript, named outlet
```

- `lib/parse-pods.js` parses this by hand (no markdown library): frontmatter
  via a `---`/`---` regex, entries via `## YYYY-MM-DD` headings, the first
  line after a heading as the headline (stripped of `**`), and optional
  trailing `Tickers: ...` / `Sources: ...` lines pulled out separately (the
  former into ticker tags, the latter into a citation line under the entry).
  It's a standalone module (not inlined in `scripts/build.js`) specifically
  so `api/update-market-pulse.js` can also require it at runtime — see
  Watchlist quotes below.
- Entries are always sorted newest-first at build time regardless of source
  order, so pod leads can technically append anywhere, but the convention
  (and the starter files) is newest-at-top.
- `pinned: true` (frontmatter, per-pod) moves that pod to the front of the
  nav and homepage grid; the rest are alphabetical. Computed in
  `computeNavOrder()` in `scripts/build.js` — there's no separate config file
  for nav order.
- `sample: true` (frontmatter, per-pod) renders a small banner on that pod's
  page disclosing its entries are placeholder/demo content, not real
  research. Currently set on `financials-real-estate.md`; remove it once real
  briefs replace the samples.
- An optional `## Watchlist` heading (parsed by `parseWatchlist()` in
  `lib/parse-pods.js` before `parseEntries()` runs, so it never gets mistaken
  for a dated entry) pulls out `- $TICKER: note` lines into the pod page's
  "Securities to Note" sidebar (`renderWatchlistSidebar()` in
  `scripts/build.js`). Can appear anywhere in the file; no sidebar renders if
  the section is absent or empty. Each ticker's live price comes from
  `data/watchlist-quotes.json` at runtime (see Watchlist quotes below) — the
  build itself has no live price to bake in.
- The seven pod slugs (and their filenames) are hardcoded in the `PODS` array
  in `templates/partials.js` — that's the single source of truth for which
  pods exist and their fallback names. `scripts/build.js` imports it to know
  which content files to expect; **display order** is computed separately
  from frontmatter (see `pinned` above), not from this array's order.

## Masthead structure: Home / Archive / About tabs

The masthead (`renderNav()` in `templates/partials.js`) is two-tier: the
`.masthead-top` row has the wordmark on the left and three primary tabs
(Home, Archive, About) on the right; the `.site-nav` row below has the seven
sector-pod links. Don't add the pod links to `.masthead-top`, and don't add
Archive/About into the sector-nav row — that split is deliberate (site-level
navigation vs. sector sub-navigation).

- **Archive** (`renderArchivePage()` in `scripts/build.js`) flattens every
  pod's `entries` array into one list, tags each with its pod name/link,
  sorts newest-first, and writes `public/archive.html` as a lightweight index
  (date + headline only, not full articles — the full read stays on each
  pod's own page). No new persistence; purely a build-time aggregation.
- **About** (`renderAboutPage()`) is static copy explaining what the site is,
  how the daily automation works, and data sources. Keep it in sync with
  reality when the automation changes — it's the one page a skeptical reader
  (or recruiter) is likely to actually read closely.

## Personal pinning vs. editorial pinning

Two unrelated features both called "pinning" — don't conflate them:

- **Editorial pin** (`pinned: true` in a pod's frontmatter): changes the
  published order for every visitor, requires editing and committing that
  pod's file. See `computeNavOrder()`.
- **Personal pin** (the star button next to the pod name on its page, added
  in `renderPodPage()`): a per-browser preference stored in `localStorage`,
  wired up entirely client-side by `src/js/pod-star.js`. It reorders
  `#pods-grid` on the homepage for that visitor only — nothing is written
  back to the site, no server involved. This is the only way for a feature
  like this to exist at all given the "no login, no database" constraint.

## The dynamic pieces: Market Pulse, Watchlist quotes, and sector briefs

`api/update-market-pulse.js` runs daily via the `crons` entry in
`vercel.json`. It checks whether today is a US trading day
(`api/lib/nyse-calendar.js`), and if so, does three things in the same run:

1. Fetches macro data via `api/lib/market-data-finnhub.js` and commits
   `data/market-pulse.json`.
2. Calls `collectAllWatchlistTickers()` (`lib/parse-pods.js`) to find every
   ticker across every pod's `## Watchlist` section, fetches a quote for each
   via `fetchWatchlistQuotes()` (`api/lib/market-data-finnhub.js`), and
   commits `data/watchlist-quotes.json`.
3. For each pod in `PODS` (in parallel via `Promise.all` — each writes a
   different file, so there's no shared-state conflict, and running them
   sequentially would risk the function's duration limit), fetches news for
   that pod's three `bellwethers` via `fetchCompanyNews()`, pools and dedupes
   the headlines (news from several companies, not one, is what lets the
   brief read as sector-wide rather than a single-stock recap), calls
   `generateSectorBrief()` (`api/lib/anthropic-client.js` — explicitly
   instructed to write about the sector broadly, using individual companies
   only as supporting examples) to write a headline/body/tickers from those
   real headlines, builds the `Sources:` line from the headlines' actual
   outlet names (never asks the model to invent sourcing), and calls
   `prependEntry()` (`lib/parse-pods.js`) to splice the result into that
   pod's `content/pods/<slug>.md` before committing it. A single pod's
   failure is caught and logged, not thrown — it shouldn't block the other
   six.

All commits go through `api/lib/github-commit.js` (GitHub's "create or
update file contents" API — a real `git commit` isn't possible from inside a
serverless function). Each push triggers Vercel's normal auto-deploy, which
copies the updated JSON into `public/data/` and regenerates every pod page
with its new entry on the next build. The market-pulse/watchlist JSON is
fetched client-side (`src/js/market-pulse.js`, `src/js/watchlist-quotes.js`);
new pod entries just show up as regular static HTML.

Because steps 2–3 read `content/pods/*.md` off disk via a dynamically-built
path (not a static `require()`/`readFileSync()` call Vercel's file-tracer can
follow), `vercel.json` has an explicit `functions.includeFiles` entry for
this function so those markdown files actually end up in the deployed
function bundle. It also sets `maxDuration: 60` to give the seven parallel
Finnhub+Claude round trips headroom. If watchlist quotes or sector briefs
stop updating in production while Today's Brief keeps working, check this
config first.

Two easy-to-forget maintenance points (documented in more detail in
`README.md` and in a comment at the top of `api/update-market-pulse.js`):

- The cron's UTC hour needs a manual ±1 nudge in `vercel.json` after each US
  daylight-saving transition (mid-March, early November) to stay ~1 hour
  before market open.
- Vercel Hobby plan only allows one cron run/day with ~±59 minute timing
  precision — that's expected, not a bug.

If Finnhub ever needs to be swapped for another provider, only
`api/lib/market-data-finnhub.js` should need to change — it exports
`fetchMarketData()` and `fetchWatchlistQuotes()` with fixed return shapes;
write a sibling module with the same exports and swap the `require(...)` in
`api/update-market-pulse.js`.

## Closed-market banner

The cron doesn't write anything on a non-trading day, so `data/market-pulse.json`
can legitimately be a day or more stale on a weekend/holiday — that's fine,
but a visitor needs to be told, not left assuming stale content is today's.
`src/js/market-pulse.js` handles this entirely client-side: it fetches
`data/nyse-holidays.json` (copied into `public/data/` at build time,
alongside the market-pulse/watchlist JSON) and re-derives "is today a trading
day" on every page load, mirroring the weekday+holiday check in
`api/lib/nyse-calendar.js`. This is deliberately independent of the stored
JSON's own state — checking freshly client-side catches every weekend and
holiday even if the cron never ran or the stored data predates today by
several days. If it's not a trading day, `#market-status` (hidden by default)
is un-hidden with an explanation; separately, the byline's own date label
switches from "Updated:" to "Most recent brief:" whenever the stored
`asOf`'s Eastern calendar date doesn't match today's — a distinct check, since
staleness and "is today closed" aren't the same question.

## Working conventions

- Never hand-edit generated HTML in `public/` — it's regenerated on every
  build and is gitignored. Edit `templates/partials.js` (shared chrome) or
  `scripts/build.js` (page rendering logic) instead.
- Never add a dependency to solve something Node's standard library or a
  dozen lines of hand-written code already handles — that's a deliberate
  project constraint, not an oversight.
- `data/market-pulse.json` in the repo is a real file (not just a build
  artifact) because it's committed by the serverless function and also
  serves as the pre-cron placeholder shown before the first run ever fires.
